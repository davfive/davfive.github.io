CCA-F · Domain 1 · Task Statement 1.7

Session State, Resumption & Forking

Resuming a session is a bet that the old context is still true.

Two ways to continue past work

--resume <session-name> continues a specific named prior conversation — useful for picking up a long-running investigation across work sessions. fork_session branches off from a shared analysis baseline to explore genuinely divergent approaches (two different refactoring strategies, say) without redoing the shared setup work for each.

The staleness trap

Resuming assumes prior context is still valid. If files the agent already analyzed have changed since, the agent doesn't know that unless you tell it — resuming silently carries forward now-incorrect assumptions. The guide's fix is targeted, not wholesale: inform the resumed session about the specific changes, so it re-analyzes just those files rather than everything.

Sometimes the better call is to skip resumption entirely: starting a new session with an injected structured summary is more reliable than resuming one where the underlying tool results have gone stale.

Check your understanding

Scenario
You resume a named session from yesterday to continue a refactoring task, but overnight a teammate changed several files the agent had already analyzed. The agent's first response in the resumed session references the old, now-incorrect file contents. What should you have done differently?
AInform the resumed session about the specific file changes so it knows to re-analyze them.
BStart a completely new session from scratch and re-explore the entire codebase again.
CIncrease the context window so the session can hold both old and new file versions at once.
DAsk the agent to always re-read every file at the start of every resumed session automatically.
Correct Resumption assumes prior context is still valid. When specific files changed, telling the agent exactly what changed lets it re-analyze just those files — the targeted fix, versus full re-exploration.
Not quite Starting over discards everything still valid from the prior session to fix a problem that only affects a few files. A bigger context window doesn't solve staleness — having both versions present doesn't tell the model which one is current. Blanket re-reading on every resume is wasteful for large codebases and defeats the purpose of resuming a session at all.
