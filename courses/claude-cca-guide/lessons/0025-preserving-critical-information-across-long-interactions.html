CCA-F · Domain 5 · Task Statement 5.1

Preserving Critical Information Across Long Interactions

Summarization is lossy by design. The question is what you let it lose.

What progressive summarization quietly drops

Condensing a long conversation into a summary is necessary, but doing it naively tends to blur exactly the details that matter most: numerical values, percentages, dates, and customer-stated expectations get smoothed into vague paraphrase. Separately, the "lost in the middle" effect means models reliably attend to the beginning and end of long inputs, but can quietly drop findings buried in the middle.

Tool output bloat A single order lookup might return 40+ fields when only 5 are actually relevant to the conversation. Left unfiltered, that noise accumulates in context across many tool calls, consuming token budget disproportionately to its value.

The fix pattern

Extract the transactional facts that actually matter (amounts, dates, order numbers, statuses) into a persistent "case facts" block carried in every prompt, kept outside the summarized/compressible history — so it can't be blurred away. Trim verbose tool output down to only the relevant fields before it accumulates. When aggregating results from multiple sources, put key findings up front (not buried mid-document) and use explicit section headers to counteract the middle-attention effect. And have subagents attach real metadata (dates, sources, methodology) to their structured outputs, so downstream synthesis has what it needs without re-deriving it.

Check your understanding

Scenario
A customer support agent has been in a long conversation with a customer. Midway through, it summarizes the conversation so far to save context, and afterward it can no longer recall the exact refund amount ($47.32) the customer was promised three turns earlier — it now just says "a refund." What's the most effective fix?
AExtract transactional facts like the exact refund amount into a persistent case-facts block outside the summarized history.
BIncrease the model's context window so summarization is no longer necessary at any point in the conversation.
CInstruct the model to write longer, more detailed summaries covering everything discussed so far.
DAsk the customer to restate the promised refund amount whenever the agent seems to have lost track of it.
Correct This is exactly the guide's named fix: numeric and transactional facts get blurred by progressive summarization, so pulling them into a separate persistent block outside the summarized text protects them from that lossy compression.
Not quite A bigger window delays the problem but doesn't solve it for genuinely long conversations, and doesn't address that even a full context can suffer the lost-in-the-middle effect. Longer summaries still summarize — the instruction doesn't guarantee specific numbers survive the compression. Asking the customer to repeat information already given is a poor experience and treats a fixable system limitation as the customer's problem.
