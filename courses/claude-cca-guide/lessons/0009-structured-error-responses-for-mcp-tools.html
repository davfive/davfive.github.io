CCA-F · Domain 2 · Task Statement 2.2

Structured Error Responses for MCP Tools

A generic "operation failed" message hides exactly the information an agent needs to recover intelligently.

The isError pattern

MCP's isError flag communicates tool failure back to the agent — but the flag alone isn't enough. The guide distinguishes four categories: transient (timeouts, service unavailability), validation (invalid input), business (policy violations), and permission errors. A uniform "Operation failed" response collapses all four into one undifferentiated signal, and an agent that can't tell them apart can't react appropriately — it might retry a permission error forever, or give up on a transient one it should have retried.

What to actually return

  • errorCategory (transient / validation / business / permission)
  • isRetryable boolean — with retryable: false plus a customer-friendly explanation for business-rule violations specifically
  • A human-readable description the agent can relay or reason from
A subtler distinction An access failure (timeout — needs a retry decision) is not the same as a valid empty result (the query succeeded; there's just nothing to return). Conflating the two — treating "no matches" the same as "couldn't check" — is its own bug.

Within multi-agent systems: have subagents attempt local recovery for transient failures themselves, and only propagate to the coordinator the errors they genuinely can't resolve — along with partial results and what was already attempted.

Check your understanding

Scenario
An order-lookup tool returns the exact same generic message, "Operation failed," whether the order doesn't exist, the request timed out, or the customer isn't authorized to view it. The agent responds identically in all three cases by simply retrying the call. What's the most effective fix?
AReturn structured error metadata including errorCategory, an isRetryable flag, and a human-readable description.
BHave the agent retry each failed call up to five times before giving up and reporting failure.
CAdd a system prompt instruction telling the agent to interpret failures more intelligently overall.
DLog all failures to a monitoring dashboard so engineers can investigate patterns after the fact.
Correct Uniform error text hides exactly the information the agent needs to react correctly — a timeout should be retried, a missing order shouldn't, and a permission error should be explained, not retried. Structured metadata is what makes that distinction possible.
Not quite Blindly retrying wastes calls on non-retryable failures like permission errors. Asking the model to "interpret more intelligently" asks it to infer distinctions from a message that structurally contains none — there's nothing to interpret. Logging for later investigation is useful for observability but does nothing to change the agent's real-time behavior.
