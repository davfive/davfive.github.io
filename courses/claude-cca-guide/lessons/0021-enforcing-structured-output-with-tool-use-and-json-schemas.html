CCA-F · Domain 4 · Task Statement 4.3

Enforcing Structured Output with Tool Use & JSON Schemas

Tool use eliminates one whole category of failure. It does not eliminate all of them.

What tool_use with schemas guarantees

Defining an extraction tool with a JSON schema as its input, then reading the structured arguments off the tool_use response, is the most reliable way to get guaranteed schema-compliant output — it eliminates JSON syntax errors as a category entirely.

Syntax-valid is not the same as correct A strict schema stops the model from returning malformed JSON. It does nothing to stop semantic errors — line items that don't sum to the stated total, a value placed in the wrong field. Those need separate validation (see Task 4.4).

tool_choice, precisely

  • "auto" — model may return plain text instead of calling a tool
  • "any" — model must call some tool, but chooses which; useful when several extraction schemas exist and the document type isn't known ahead of time
  • Forced ({"type": "tool", "name": "extract_metadata"}) — guarantees a specific tool runs, e.g. before enrichment steps depend on its output

Schema design choices that prevent fabrication

Mark fields optional/nullable when the source document may genuinely not contain that information — a required field the model can't find otherwise gets fabricated to satisfy the schema. Use enum fields with an "other" + free-text detail pattern (or an explicit "unclear" value) for categories that don't cleanly fit a fixed list.

Check your understanding

Scenario
An invoice-extraction tool has a required "purchase_order_number" field. On invoices that never included a PO number, the model started fabricating plausible-looking numbers to satisfy the schema. What's the most effective fix?
AMake purchase_order_number optional/nullable so the model can omit it rather than invent a value.
BSwitch tool_choice from a forced tool to "auto" so the model can skip the extraction entirely.
CAdd a system prompt instruction telling the model never to fabricate purchase order numbers.
DAdd a second validation-only tool call that re-checks the purchase order number after extraction.
Correct This is the guide's exact prevention mechanism: a required field the model can't find gets fabricated to satisfy the schema — making the field optional/nullable removes that pressure entirely.
Not quite Switching to "auto" risks losing structured output altogether rather than fixing the one problematic field. A prompt instruction is a soft patch on a structural incentive — the schema itself is still telling the model the field is required. A second validation pass can catch the fabrication after the fact but doesn't remove the incentive that caused it.
