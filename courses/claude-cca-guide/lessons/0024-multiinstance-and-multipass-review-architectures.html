CCA-F · Domain 4 · Task Statement 4.6

Multi-Instance & Multi-Pass Review Architectures

The model that wrote the code is structurally the worst-positioned reviewer of that same code.

Why self-review underperforms

A model that just generated code retains the reasoning context behind its own decisions in that same session — which makes it less likely to question those decisions when asked to review them. This holds even when explicitly instructed to "review carefully" or given extended thinking; the limitation isn't effort, it's the shared context itself. An independent review instance, without that prior reasoning context, catches subtle issues more reliably.

Multi-pass for large reviews Splitting a large multi-file review into per-file local-analysis passes plus a separate cross-file integration pass avoids two problems at once: attention dilution (too much to track in one pass) and contradictory findings (different parts of one pass disagreeing with themselves).

A further refinement: have each pass self-report a confidence score alongside its findings, so review effort (including human attention) can be routed toward the lower-confidence findings first — this connects directly to Task 5.5's confidence-calibration approach.

Check your understanding

Scenario
The same Claude session that just implemented a complex refactor across 12 files is then asked, in that same session, to carefully review its own changes for bugs. The review comes back clean, but a subtle cross-file data-flow bug is later found in production. What change would most effectively have caught it?
AUse a second, independent Claude instance with no prior reasoning context to review the changes.
BAsk the same session to review again, this time with extended thinking enabled for more careful analysis.
CAsk the same session to review again, with an explicit instruction to be more skeptical of its own work.
DReduce the refactor's scope to fewer files so the same session can review more thoroughly.
Correct This is the guide's core distinction: the limitation is the shared reasoning context, not effort or instruction. An independent instance without that context is structurally better positioned to catch what the generator is unlikely to question.
Not quite Extended thinking and stronger skepticism instructions both keep the same underlying limitation in place — the session still carries the reasoning that produced the bug in the first place. Shrinking scope might reduce total surface area but doesn't address why the generating session is a weak reviewer of its own work regardless of size.
