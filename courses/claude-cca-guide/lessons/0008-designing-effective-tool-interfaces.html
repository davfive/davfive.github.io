CCA-F · Domain 2 · Task Statement 2.1

Designing Effective Tool Interfaces

The model picks a tool almost entirely based on its description. Treat the description as the interface.

Descriptions are the selection mechanism

Tool descriptions are the primary signal an LLM uses to decide which tool to call. Minimal descriptions ("Retrieves order details") lead to unreliable selection whenever a similar tool exists nearby. Good descriptions include input formats, example queries, edge cases, and explicit boundaries: not just what the tool does, but when to use it instead of the similar-looking alternative.

The classic failure Two tools with near-identical descriptions — analyze_content and analyze_document — cause consistent misrouting. Neither description tells the model what distinguishes them.

Two fixes beyond better wording

Sometimes the right fix is renaming and re-describing (turn analyze_content into extract_web_results with a web-specific description). Sometimes it's splitting an overly generic tool into purpose-specific ones with defined input/output contracts — analyze_document becomes extract_data_points, summarize_content, and verify_claim_against_source, each unambiguous on its own.

One more failure mode worth knowing: system prompt wording can be keyword-sensitive enough to override a perfectly good tool description, creating unintended associations you didn't design for. Worth checking when tool selection looks wrong despite descriptions that read fine in isolation.

Check your understanding

Scenario
Your agent has two MCP tools: fetch_invoice ("Retrieves invoice information") and fetch_payment ("Retrieves payment details"). When users ask "why was I charged $49.99 last month," the agent inconsistently calls one, the other, both, or neither correctly. What's the most effective first step?
AExpand each tool's description with input formats, example queries, and explicit boundaries versus the other.
BAdd several few-shot examples showing which tool to call for various types of billing questions.
CMerge both tools into a single get_billing_info tool that accepts any billing-related identifier.
DAdd a routing step that scans user messages for keywords before either tool becomes available.
Correct Tool descriptions are the model's primary selection signal. Minimal, overlapping descriptions are the root cause here — expanding them with concrete boundaries is the lowest-effort, highest-leverage fix, and it's the guide's stated first step.
Not quite Few-shot examples add real value eventually, but they treat a symptom (inconsistent selection) rather than the root cause (vague descriptions), and add token overhead before the cheaper fix has been tried. Merging the tools is a legitimate architectural option, but it skips past the low-effort fix that should come first. A keyword-based routing step reintroduces a rigid pre-classifier that bypasses the model's own language understanding — over-engineered as a first step.
