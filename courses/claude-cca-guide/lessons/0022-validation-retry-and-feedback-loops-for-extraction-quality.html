CCA-F · Domain 4 · Task Statement 4.4

Validation, Retry & Feedback Loops for Extraction Quality

Retries fix format problems. They cannot fix information that was never there.

Retry-with-error-feedback

When a semantic validation error is caught (values don't sum, a field holds the wrong type of data), the effective retry pattern appends the specific error to the prompt and asks the model to self-correct — including the original document, the failed extraction, and the exact validation error, so the model has everything it needs to fix the specific problem rather than guess.

Know when retry can't help If required information is simply absent from the source document, no amount of retrying produces it — that's a genuinely different failure than a format or structural error, and needs a different response (flag for review, mark null) rather than another retry cycle.

Building a feedback loop, not just a retry

Add a detected_pattern field to structured findings so that when developers dismiss a finding, you can systematically analyze which code constructs are triggering false positives. For numeric extraction specifically: extract both a calculated_total and the document's stated_total to flag discrepancies automatically, and add a conflict_detected boolean when source data is internally inconsistent.

Check your understanding

Scenario
An invoice extraction pipeline occasionally returns a stated_total that doesn't match the sum of line items. Separately, some invoices are missing a required customer tax ID entirely because the field simply isn't present on that invoice template. Which approach correctly handles both cases?
ARetry with the specific sum-mismatch error for the totals case; mark tax ID null rather than retrying for the missing case.
BRetry both cases up to three times each with the same generic "please recheck your extraction" prompt.
CTreat both as the same category of error and route both to human review without attempting any retry.
DIncrease model temperature on retry so a different total and tax ID are more likely to be generated.
Correct This distinguishes exactly the two failure types the guide separates: a sum mismatch is a semantic error retry-with-feedback can fix, while a genuinely absent tax ID is information retrying can't produce — nullable handling is the correct response there instead.
Not quite A generic retry prompt without the specific error wastes a retry cycle on the totals case and can't help at all with truly missing information. Routing everything to human review discards retries that would actually succeed on the fixable case. Raising temperature adds randomness without addressing either the specific math error or the field's genuine absence.
