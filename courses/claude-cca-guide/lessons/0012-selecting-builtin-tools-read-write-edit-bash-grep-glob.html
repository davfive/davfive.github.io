Selecting Built-in Tools (Read, Write, Edit, Bash, Grep, Glob)

Each built-in tool has a job it's actually good at. Using the wrong one is a common, fixable inefficiency.

What each tool is actually for

  • Grep — content search: finding patterns like function names, error messages, or import statements inside file contents
  • Glob — file path pattern matching: finding files by name or extension pattern
  • Read / Write — full file operations
  • Edit — targeted modification via unique text matching; when the anchor text isn't unique, Edit fails, and the reliable fallback is Read + Write instead

Build understanding incrementally

The efficient pattern for exploring an unfamiliar codebase: start with Grep to find entry points, then use Read to follow imports and trace flow — rather than reading every file upfront. For tracing a function's usage across wrapper/re-export modules specifically: first identify all the exported names (including re-exports), then Grep for each of those names across the codebase, since a single direct-name search would miss anything called through a wrapper.

Check your understanding

Scenario
You need to rename a function that's called from many places across a large codebase — some through direct imports, some through re-exporting wrapper modules. What's the most effective approach to reliably find every usage?
AUse Grep to find all exported names of the wrapper modules, then Grep again for each of those names across the codebase.
BUse Read to open every file in the repository and manually scan each one for references to the function.
CUse Glob to find all files with a .js or .ts extension and assume the function is used somewhere among them.
DUse Edit to rename the function in its original definition file and rely on IDE tooling to catch the rest.
Correct This is the guide's tracing pattern for wrapper modules: first identify all exported names, including re-exports, then Grep for each one across the codebase — catching indirect usages a single search would miss.
Not quite Reading every file is exhaustive but doesn't scale, and manual scanning misses things a targeted search wouldn't. Glob only narrows by file type, not by actual usage — it doesn't locate anything by itself. Editing the definition and relying on outside IDE tooling assumes capabilities outside the agent and skips the actual investigation, likely missing re-exported call sites.
