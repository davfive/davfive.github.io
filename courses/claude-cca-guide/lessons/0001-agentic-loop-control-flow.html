CCA-F · Domain 1 · Task Statement 1.1

Agentic Loop Control Flow

The exam's precise vocabulary for something you already do every day — and the three anti-patterns it's designed to catch you on.

You already write agentic loops. This lesson isn't teaching you what one is — it's mapping your working knowledge onto the exact terms and failure modes the exam tests.

The lifecycle, in exam terms

Every agentic loop iteration has the same shape: send a request to Claude, inspect stop_reason on the response, act accordingly, repeat.

  • stop_reason: "tool_use" — Claude wants to call one or more tools. Execute them, append the results to conversation history, send another request.
  • stop_reason: "end_turn" — Claude is done. Return the final response; stop looping.

That's the entire control-flow decision. The exam frames this as the distinction between model-driven decision-making (Claude reasons about what to do next based on accumulated context) and pre-configured decision trees (you hard-code a fixed tool sequence). The loop's job is to faithfully execute whichever tool calls the model requests — not to second-guess or pre-route them.

while True:
    response = client.messages.create(..., tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason == "tool_use":
        results = [run_tool(block) for block in response.content if block.type == "tool_use"]
        messages.append({"role": "user", "content": results})
        continue  # loop again — model needs to see the results

    if response.stop_reason == "end_turn":
        break  # done

The three anti-patterns the exam is built around

The Exam Guide names these explicitly. Every wrong answer on a Task 1.1 question is almost always one of these three, dressed up differently.

Anti-pattern 1 Parsing natural-language signals to decide when the loop should stop — e.g. checking whether the assistant's text contains "I'm done" or "task complete." Models phrase completion inconsistently. This produces both false stops (loop ends while tools were still needed) and false continues (loop keeps going after real completion).
Anti-pattern 2 Setting an arbitrary iteration cap as the primary stopping mechanism. A cap is a reasonable safety net against runaway loops — but if it's doing the actual job of deciding when work is finished, you'll cut off legitimate multi-step work or let simple tasks run needlessly long.
Anti-pattern 3 Treating the presence of assistant text content as a completion indicator. Claude can emit text alongside a tool call (e.g. "Let me check that for you" followed by a tool_use block) — text existing doesn't mean the turn is over. Only stop_reason tells you that.
The only reliable signal stop_reason is a structured field the API guarantees. Everything else — text content, phrasing, iteration count — is either unreliable or a secondary safety measure, never the primary mechanism.

Check your understanding

Scenario
Your agentic loop checks whether the assistant's response text contains the phrase "I have completed the task" to decide when to stop calling tools. In production, the loop sometimes terminates early even though tool calls were still pending, and sometimes keeps looping after the task is genuinely finished. What's the most effective fix?
ACheck whether stop_reason equals end_turn instead of parsing assistant text for completion phrases.
BCount loop iterations and stop once a fixed maximum has been reached, regardless of state.
CAsk the model to output a JSON field named done before inspecting the response at all.
DSwitch to a shorter system prompt so completion phrasing becomes more consistent overall.
Correct stop_reason is the API's structured signal for why generation stopped — "tool_use" means Claude wants to call a tool, "end_turn" means it's finished. Parsing phrases like "I have completed the task" is exactly the anti-pattern the guide names: text-based signals are fragile in both directions.
Not quite B (arbitrary iteration caps) is a named anti-pattern — it's a safety net, not a termination signal, and can cut work off early or let it run too long. C moves the same fragility into a schema field instead of removing it; the model can still omit or misreport it. D doesn't touch the root cause: the loop still isn't using the structured field the API already provides. The fix is always the same — check stop_reason.
Scenario
You're debugging an agent that, each turn, rebuilds its prompt from only the original user request — it never includes results from tools called in earlier turns. The agent frequently repeats the same tool call or contradicts findings from two turns earlier. What's the root cause?
ATool results must be appended to conversation history so the model can reason about them later.
BThe system prompt should instruct the model to remember its previous tool calls more carefully.
CThe loop should reduce the number of available tools so fewer results need to be tracked.
DThe model should summarize each tool result into one sentence before the next iteration starts.
Correct The loop's memory is the conversation history sent with each request. Tool results have to be appended to it for the model to "remember" what it already found — rebuilding from scratch each turn throws that away, so repeats and contradictions are the expected outcome, not a prompting bug.
Not quite B tries to fix a structural problem with an instruction — the model can't reason about information it was never given, no matter how the prompt is worded. C reduces symptoms, not the cause: even one tool's results still need to persist across turns. D adds an unneeded step; summarizing may help with context budget later, but the actual defect here is that results aren't in context at all. The fix is structural: append results to history.
