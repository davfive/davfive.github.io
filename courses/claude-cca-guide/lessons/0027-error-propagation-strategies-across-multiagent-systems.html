CCA-F · Domain 5 · Task Statement 5.3

Error Propagation Strategies Across Multi-Agent Systems

What a coordinator can do with a failure depends entirely on how much context that failure carries with it.

Structured error context enables real decisions

A subagent reporting a failure should include: the failure type, what was actually attempted, any partial results already obtained, and potential alternative approaches. That's what lets a coordinator make an intelligent recovery decision instead of guessing.

Access failure vs. valid empty result A timeout (access failure, needs a retry decision) and a successful query that legitimately found nothing (valid empty result) are not the same thing and shouldn't be reported the same way — conflating them is a recurring bug class (see also Task 2.2).

Two named anti-patterns

Silently suppressing an error by returning empty results as if they were a success hides a real failure from the coordinator. Terminating the entire workflow on a single subagent failure is the opposite overcorrection — it throws away everything that did succeed. The better pattern: subagents attempt local recovery for transient failures themselves, and only propagate upward what they genuinely can't resolve, along with what was attempted and any partial results. Synthesis output should carry coverage annotations distinguishing well-supported findings from areas with real gaps due to unavailable sources.

Check your understanding

Scenario
In a multi-agent research pipeline, one subagent's web search for a specific subtopic times out. The subagent returns an empty result set with no further detail, indistinguishable from a successful search that simply found no relevant results. The coordinator proceeds as if that subtopic has no available information. What's the most effective fix?
AHave the subagent report structured error context distinguishing a timeout from a genuine empty result, with what was attempted.
BTerminate the entire pipeline whenever any single subagent search fails, to avoid presenting incomplete findings.
CHave the coordinator re-run the entire pipeline from scratch whenever any subagent returns zero results.
DInstruct subagents to always return at least one result, even a low-relevance one, to avoid empty result sets.
Correct This is the exact conflation the guide flags as a bug: an access failure (timeout) and a valid empty result look identical without structured context, and that difference is exactly what the coordinator needs to decide whether to retry.
Not quite Terminating the whole pipeline over one subagent's failure is the named overcorrection anti-pattern — it discards everything that succeeded elsewhere. Re-running everything from scratch is wasteful when only one subtopic actually failed. Forcing a low-relevance result to avoid "empty" output actively hides the real problem rather than surfacing it.
