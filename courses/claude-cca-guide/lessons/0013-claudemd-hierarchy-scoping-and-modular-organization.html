CLAUDE.md Hierarchy, Scoping & Modular Organization

Three levels of CLAUDE.md exist for a reason — mixing them up is the most common team-config bug.

The three levels

  • User-level (~/.claude/CLAUDE.md) — applies only to that person. Never shared via version control, so teammates never see it.
  • Project-level (.claude/CLAUDE.md or root CLAUDE.md) — shared with the whole team through the repo.
  • Directory-level — subdirectory-scoped CLAUDE.md files for package- or module-specific conventions.
The named diagnostic case A new team member isn't receiving instructions the rest of the team relies on. Root cause: those instructions were written into someone's user-level file, not the project-level one — so they were never in version control for anyone else to inherit.

Keeping it modular

Two tools prevent a single sprawling CLAUDE.md: the @import syntax, for pulling in specific standards files relevant to a given package (so a maintainer only imports what applies to their domain), and a .claude/rules/ directory, for splitting a monolith into focused topic files like testing.md, api-conventions.md, deployment.md. When behavior seems inconsistent across sessions, the /memory command shows exactly which memory files are actually loaded — the fastest way to diagnose a hierarchy mismatch.

Correct This is the guide's named diagnostic case exactly: instructions living in one person's user-level file never propagate to teammates, since user-level config isn't version-controlled. /memory is the tool built to surface exactly this mismatch.
Not quite There's no editor-restart or first-commit gate on CLAUDE.md loading — those aren't real mechanisms. Manually retyping defeats the entire point of project-level config being shared automatically via version control.
