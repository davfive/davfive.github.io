Integrating MCP Servers into Claude Code Workflows

Where a server is scoped, and whether it's custom-built, are both deliberate decisions — not defaults.

Two scopes, two purposes

Project-level .mcp.json is for shared team tooling, committed to version control so everyone gets the same servers. User-level ~/.claude.json is for personal or experimental servers that shouldn't be forced on teammates. Environment variable expansion (${GITHUB_TOKEN}) inside .mcp.json keeps credentials out of committed config entirely.

Tools from every configured server are discovered at connection time and made simultaneously available — which is exactly why scoping and tool distribution (previous lesson) both matter here too.

Build vs. adopt

Prefer existing, actively-maintained community MCP servers for standard integrations (Jira, for instance) over building your own. Reserve custom server development for genuinely team-specific workflows that no existing server covers.

Resources cut down exploratory calls

MCP resources expose content catalogs — issue summaries, documentation hierarchies, database schemas — directly, so the agent has visibility into what's available without needing exploratory tool calls just to find out what exists. Related: enhance MCP tool descriptions enough that the agent doesn't default to a weaker built-in tool (like Grep) when a more capable MCP tool is actually the better choice.

Check your understanding

Scenario
Your team built a custom MCP server for Jira integration, duplicating functionality an actively maintained community Jira MCP server already provides. Meanwhile, a teammate commits their personal experimental weather-API MCP server config directly into the shared project .mcp.json. What are the two changes that best align with recommended practice?
AAdopt the community Jira server instead of the custom one, and move the experimental server to user-scoped config.
BKeep the custom Jira server for full control, and leave the experimental server in the shared project config.
CMerge the custom Jira server and the experimental server into a single combined MCP server for simplicity.
DRemove both servers and rebuild all integrations from scratch using only officially documented tools.
Correct The guidance here is specific: prefer existing community servers over custom builds for standard integrations like Jira, and personal/experimental servers belong in user-scoped ~/.claude.json, not the shared project file everyone pulls.
Not quite Keeping the custom Jira server retains unnecessary duplicated maintenance, and leaving an experimental tool in shared config puts it in front of the whole team unnecessarily. Merging two unrelated servers muddies scoping further for no real benefit. Rebuilding everything from scratch is a drastic overcorrection — nothing is wrong with MCP servers generally, just these two specific placement choices.
