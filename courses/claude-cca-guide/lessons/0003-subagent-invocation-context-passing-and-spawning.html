CCA-F · Domain 1 · Task Statement 1.3

Subagent Invocation, Context Passing & Spawning

Spawning a subagent is one line. Getting it the right context, and getting true parallelism, is the actual skill.

How spawning actually works

The Task tool is the mechanism a coordinator uses to spawn subagents — and the coordinator's own allowedTools must include "Task", or it simply can't delegate at all. Each subagent type is configured via an AgentDefinition: a description, a system prompt, and tool restrictions specific to that role.

The isolation point from the last lesson applies here directly: a spawned subagent gets no automatic context. Whatever it needs — prior findings, tool results, source excerpts — has to be written into its prompt explicitly, using structured formats that separate content from metadata (source URLs, document names, page numbers) so attribution survives.

Parallelism is a response-structure decision

If a coordinator has three independent subtasks, spawning them one at a time across three separate turns — waiting for each to finish before starting the next — gets you sequential execution by accident. True parallel execution comes from emitting multiple Task tool calls within a single coordinator response.

Write goals, not scripts

Coordinator prompts that specify the research goal and quality bar ("find load-bearing evidence for X, cross-check with at least two sources") let a subagent adapt its approach. Step-by-step procedural instructions lock it into one path even when that path turns out to be wrong.

Check your understanding

Scenario
A coordinator has three fully independent subtasks. It currently emits one Task tool call, waits for that subagent to finish, then emits the next — one per turn, three turns total. What's the most effective change to get true parallel execution?
AEmit all three Task tool calls within a single coordinator response so the subagents run in parallel.
BMerge the three subtasks into one larger subagent to avoid coordination overhead entirely.
CIncrease the coordinator's context window so it can track three sequential subagents at once.
DAdd a system prompt instruction telling the coordinator to work through subtasks more quickly.
Correct Independent subtasks delegated as multiple Task calls within one response is what actually triggers parallel execution, instead of one-at-a-time sequential waits.
Not quite Merging the subtasks throws away the isolation and specialization benefits of separate subagents for no reason — they're independent, not overlapping. A bigger context window doesn't address the real issue, which is turn structure, not capacity. A speed instruction papers over a structural serialization problem instead of fixing it — the coordinator isn't slow, it's blocked waiting on each subagent sequentially by construction.
