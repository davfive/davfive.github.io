CCA-F · Domain 1 · Task Statement 1.6

Task Decomposition Strategies for Complex Workflows

Two decomposition modes, and a review-quality failure mode you've probably already hit.

Fixed pipelines vs. adaptive decomposition

Prompt chaining — a fixed sequence of steps — fits predictable, multi-aspect work where you know the shape in advance (analyze each file individually, then run one cross-file integration pass). Dynamic decomposition fits open-ended investigation, where subtasks are generated based on what's discovered at each step rather than planned upfront.

The attention-dilution failure

Reviewing many files together in one pass produces a specific, recognizable failure: inconsistent depth (some files get real scrutiny, others don't), and sometimes outright contradictions — the same pattern flagged as a bug in one file and approved in another. The fix isn't a bigger model or bigger context window; it's splitting into per-file local passes plus a separate cross-file integration pass that specifically looks for issues spanning files.

Open-ended tasks

For something like "add comprehensive tests to a legacy codebase" — no fixed shape exists upfront — map the structure first, identify high-impact areas, then build a prioritized plan that adapts as dependencies are discovered along the way.

Check your understanding

Scenario
A pull request modifies 14 files. Reviewing them all together in a single pass produces inconsistent depth — detailed feedback on some files, superficial comments on others — and even contradictory findings, with the same pattern flagged as a bug in one file and approved in another. What's the most effective restructuring?
ASplit into focused passes: analyze each file individually, then run a separate integration pass for cross-file issues.
BRequire the pull request to be split into several smaller submissions before any review begins.
CSwitch to a model with a larger context window so all 14 files fit comfortably in one pass.
DRun the review three times and only report issues that show up in at least two of the runs.
Correct This is attention dilution from processing many files at once. Per-file local passes give each file focused attention; a separate integration pass then catches the cross-file issues a per-file view alone would miss.
Not quite Splitting the PR itself shifts the burden to developers without fixing the review process. A larger context window misdiagnoses the problem — it doesn't fix inconsistent attention within that window, only how much fits inside it. Running the review three times and requiring agreement would actually suppress real findings that only show up intermittently — the opposite of what's needed.
